# 智启课源项目计划书

版本 1.0　编制日期 2026年9月4日　适用对象 项目负责人及参与开发的 AI

## 1 项目结论与使用方式

建议将本项目建设为中文优先的 AI 学习工作台，参考 DeepTutor 的页面布局和交互方式，分两条连续的交付线推进：先完成可以独立演示的前端，再接入资料问答、练习和笔记，形成可实际使用的学习流程。前端演示完成是第一个成果，不能代替后续真实功能验收。

项目暂用当前目录名称“智启课源”。本计划假设你是主要负责人，使用多个 AI 辅助产品设计、编程和检查；第一批用户为个人学习者及小范围测试用户；先做浏览器网站，中文优先，兼顾手机访问。具体学段、学科、商业模式和部署地区尚未确定，因此不预设学校采购、班级管理或收费体系。

本套材料的阅读顺序：本文件用于确定做什么；《02_项目实现详细流程》用于安排怎么做；《03_AI执行任务包》用于向每个 AI 下达任务。正文中的预算、性能和质量数值均为本项目的建议目标或估算，未表示已经完成测试。

## 3 建设目标与首个学习场景

首个演示场景选择一份可正常提取文字的中文教材 PDF。用户上传教材，创建知识库，询问一个章节概念，点击回答中的来源查看原文，要求生成 5 道练习，提交答案后得到反馈，并把解释保存为学习笔记。关闭浏览器后重新进入，能恢复会话、题目和笔记。

这条流程同时验证页面、上传、任务状态、模型调用、引用、数据库和历史恢复。先固定一个学科和一套测试资料，减少不同格式、不同学科同时引入的变量。扫描教材、复杂公式识别和多模态理解作为后续增强。

产品价值落实为三个可观察结果：资料能被找到并引用；学习过程可以继续；回答能转化为可复习的题目和笔记。首版不以模型数量、智能体数量或菜单数量作为成功指标。

## 6 实现路线选择

| 路线 | 适用情况 | 优点 | 必须承担的工作 |
| --- | --- | --- | --- |
| 在固定版本上二次开发 | 希望保留大多数 DeepTutor 能力，快速自用 | 页面和后端已有大量实现 | 熟悉其配置与依赖，维护上游差异，完整回归 |
| 独立前端加精简后端 | 重点是模仿 UI 并构建自己的产品 | 页面、数据结构和交付范围可控 | 自己完成检索、持久化和服务接口 |

默认推荐第二条，理由是你的明确要求集中在 UI 和前端页面，并计划分阶段交给多个 AI。它便于隔离任务，也避免为了展示页面先启动完整智能体系统。若你的实际目标是“完整 DeepTutor 换品牌即可使用”，则应改用第一条，沿用原项目后端和锁文件；不要同时套用本文的自建 API 和数据库方案。

允许在核查许可证后复用合适的源码片段，但每次复用都记录原路径和提交。整页复制通常还会带入上下文、鉴权、国际化、契约类型和运行时依赖，不能只复制一个 TSX 文件就当作完成迁移。

## 7 技术方案

前端建议采用 Next.js App Router、React、TypeScript、Tailwind CSS 3.4，沿用参考项目的技术家族。组件图标使用 Lucide，正文使用 Markdown 与数学公式渲染。页面默认在独立项目中实现；依赖版本在初始化时统一核实、固定并提交锁文件，不由每个 AI 自行升级。[参考项目依赖](https://github.com/HKUDS/DeepTutor/blob/e5f2d38c393497a57fda13209be55067c1740ca7/web/package.json)

后端建议使用 FastAPI 加 Python，负责用户权限、模型密钥、上传、检索和任务。结构化数据使用 PostgreSQL，文本向量使用 pgvector；文件先保存到有持久卷的专用目录，之后通过统一存储接口切换到兼容 S3 的对象存储。耗时任务进入 Redis 队列和独立 Worker。此技术组合是新项目建议，不是对 DeepTutor 后端现状的描述。

用一份 OpenAPI 规范生成前端类型；用 REST 完成增删改查，用 SSE 推送生成状态。SSE 是服务端向浏览器持续发送事件的连接。Mock 是遵循同样接口返回固定数据的替身，使前端不必等待后台完成。RAG 指回答前先从资料中检索相关原文，再把原文交给模型。

开发阶段只接一个对话模型服务和一个嵌入模型。服务端建立供应商适配层，再逐个增加其他服务；模型是否支持图像、工具调用、结构化输出和流式结果必须分别验证，不能根据名称推断。

## 8 多个 AI 的协作方式

把 AI 当作可替换的执行者，职责和交付物保持不变。用于开发的 AI 工具，与产品上线后实际调用的模型 API 是两件事，预算和配置应分开管理。

| 职责 | 输入 | 输出 | 由谁决定通过 |
| --- | --- | --- | --- |
| 产品与架构 | 本计划、目标用户、需求变更 | 页面规格、接口、决策记录 | 你 |
| 界面实现 | 截图、设计变量、组件规范 | 页面、交互、响应式截图 | 你按参考图验收 |
| 后端实现 | API、数据表、验收场景 | 服务、迁移、任务、日志 | 自动检查加人工场景 |
| 集成 | 已完成的模块分支 | 可运行的完整流程 | 指定的一位集成负责人 |
| 独立审查 | diff、测试结果、实际截图 | 可复现问题及复验结果 | 你确认高风险问题关闭 |

每个 AI 只领取一个有边界的任务，例如“知识中心列表和创建弹窗”，不要一次发送“实现整个平台”。同一时段最多让 2 个实现任务并行，接口和公共组件由一位负责人管理。不了解 Git 时先串行：一个任务完成并保存版本，再交给下一个 AI。

共享资料固定为 PRD、页面规范、API 规范、任务清单、决策记录和交接记录。修改任何公共接口时，先更新规范和 Mock，再修改两端并检查调用方。以仓库里的文件为最新状态，不以某次 AI 对话中的口头解释为准。

## 9 时间与工作量计划

以下按 1 名负责人借助 AI、每天约 4 至 6 小时有效工作估算，已经包含基础联调，但模型服务、文件解析和部署问题可能增加时间。先完成一个页面和一条 API 后，再校准后续估算。

| 阶段 | 预估有效工作量 | 主要产物 |
| --- | --- | --- |
| 需求和基线 | 12 至 20 小时 | 页面清单、截图集、固定版本、验收资料 |
| 工程与公共界面 | 24 至 36 小时 | 主题、侧栏、组件、Mock、首页 |
| 核心页面及扩展页演示 | 48 至 72 小时 | V0.2 完整前端演示 |
| 后台和学习流程 | 64 至 96 小时 | V0.3 上传、问答、练习、笔记、恢复 |
| 验收与上线试用 | 32 至 48 小时 | 测试报告、备份恢复、部署文档 |
| 返工预留 | 前述合计的约 20% | 处理集成和体验问题 |

基础合计 180 至 272 小时，加预留约 216 至 326 小时。按每周 25 小时投入，规划约 9 至 13 周。只做 V0.2 前端演示约 84 至 128 小时，可按 3 至 5 周安排。若已有成熟前后端经验，可能更快；初次开发应扩大预留。扩展功能的真实实现不包含在上述首期估算内。

里程碑按验收推进：先验收页面壳，再验收所有演示页，然后验收一条真实学习流程，最后做小范围试用。上一阶段的阻断问题未解决，不继续增加新菜单。

## 10 费用规划与成本控制

费用拆分为开发 AI 工具订阅、运行模型调用、服务器与数据库、文件存储与备份、域名及运维。已有开发工具订阅不等于产品运行 API 已免费获得。这里不提供未经核查的供应商现价；采购时按实际地区、配置和官方报价填写预算表。

模型月成本按“输入 token 数 × 输入单价 + 输出 token 数 × 输出单价”计算，统一换算计价单位；再加嵌入、解析、搜索、重试与生成等服务费用。记录每次任务的供应商、模型、用途、用量和计价版本，价格未配置时显示用量，不伪造金额。

举例仅作容量演算：20 名测试用户，每天各提问 15 次，每月按 30 天计算，得到 9,000 轮。若每轮平均输入 4,000、输出 1,000 token，则分别是 3,600 万和 900 万 token。这不是实测平均值，长资料、多轮上下文和自动重试都可能提高消耗。

为控制试用开销，设置账号日额度、单任务 token 上限、并发上限和整站月预算提醒。出题按批量生成，资料去重后再嵌入；长书生成必须在用户看到规模预估后启动。

## 11 验收目标

| 维度 | 首期建议验收方法 |
| --- | --- |
| 界面 | 在 1440×900、1024×768、390×844 固定视口检查；布局、侧栏、输入框、字号和状态一致 |
| 完整性 | 清单中的前端页面均可打开；主要按钮均有行为或明确不可用原因；无伪成功 |
| 功能 | 教材学习流程从上传到恢复能完整走通；错误输入与失败恢复可复现 |
| 回答依据 | 准备 30 个材料内问题和 10 个材料外问题；检索前 5 条命中目标段落不少于 27/30；材料外题至少 9/10 明确说明依据不足 |
| 引用 | 人工抽查 30 条引用，文档与页码或段落定位全部正确；“跳到对的页面”与“原文支持结论”分别核查 |
| 数据 | 账号 A 无法读取 B 的资料、对话、笔记及事件流；退出后受保护页面不可继续访问 |
| 性能 | 本地固定 Mock 数据下界面交互反馈不超过 200ms；真实模型首字耗时单独统计，不用假进度掩盖等待 |
| 可维护性 | 类型、构建、重要业务测试通过；完整安装和备份恢复步骤由另一位 AI 复核 |

这些质量阈值是上线前要验证的目标。它们不能证明所有学科都达到相同效果；试用初期应继续记录错误案例，并以实际材料更新测试集。

## 12 主要风险与应对

| 风险 | 早期信号 | 应对措施 |
| --- | --- | --- |
| 范围不断增加 | 核心流程未通就添加多个智能体 | 将新需求放入 V1.x，先完成当前里程碑 |
| 页面像但操作无效 | 上传始终成功、按钮只有提示 | 明确状态机和失败场景，逐项点击验收 |
| AI 修改互相覆盖 | 公共组件或 API 频繁返工 | 限定文件范围，固定负责人，小任务合并 |
| 检索或引用不可靠 | 回答流畅但找不到原文 | 固定测试集，保存原文定位，来源不足时明示 |
| 密钥或资料泄露 | 浏览器中出现模型密钥或越权资料 | 密钥只存服务端，逐资源鉴权，日志脱敏 |
| 长任务卡住 | 页面刷新后永远转圈 | 保存任务状态，提供取消、重试和重启恢复 |
| 升级造成回归 | 不同 AI 安装不同依赖版本 | 固定锁文件，集中升级，先在测试环境验证 |
